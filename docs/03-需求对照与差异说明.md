## 二、必须修正的 6 个事实（都有证据）

### 2.1 不存在 `.pac`，正确产物是 `.zip`

- 全 SDK 仓库对 `.pac` **零命中**；`pack.bat` 调 `arelease.exe` 输出 **`ML307A_DSLN_APP.zip`**。
- `.pac` 是展锐格式；你的 QFlash 是**移远**工具（内嵌展锐下载器）。
- 影响：**不要按 `.pac` 去找工具**，见 `docs/01` 第 5 节的烧录路线。

### 2.2 应用层无法运行时开关 RNDIS（链接器实证，非推测）

- 用户 APP 的可调用符号边界 = `prebuild/objs/ML307A/DSLN/cm_stub_DSLN.o`，共 **326 个符号**
  （完整清单：`docs/sdk-reference/app-link-symbols.txt`）。
- 其中 `usb` / `rndis` / `netif` / `lwip_rndis_hotplug_*` / `lwip_set_usb_forward_flag` **全部 0 命中**。
- 内核 map 里能看到 `rndis.o`、`netif_usb_set_status`、`lwip_rndis_hotplug_link` 等，
  但**那是内核镜像自身**，未导出给应用 —— 实测编译会直接报 `undefined reference`。
- 因此：
  - 原需求"若 SDK 支持运行时切换则即时生效" → **不支持**，走"重启生效"分支
  - 原需求"关闭时 RNDIS 不启用" → 应用**做不到**，只能把期望值存进配置并提示用户
- 可尝试的替代路径（需向中移 FAE 或实测确认）：底包层 AT 命令。底包 AT 表里与 USB 相关的可疑项：
  `+MDIALUPCFG`、`+MUECONFIG`（`autoconn`）、`*NETIFCM`、`*LWIPCTRL`，但**虚拟 AT 官方声明只支持 3GPP 指令**。

### 2.3 `192.168.0.1` 不存在，默认网段证据是 `192.168.0.x`

- `192.168.0.1` 的 ASCII 与两种字节序（`C0A80401` / `0104A8C0`）在底包里**各 0 次命中**。
- 唯一成体系的证据是 `at*lwipctrl=system, dhcpserver|192.168.0.1`，配套掩码
  `255.255.0.0`（**/16，不是 /24**），DHCP 池 `192.168.0.100 ~ 192.168.0.100`。
- 处置：固件**不写死任何 IP**，在拿到 PDP 地址后打印真实访问地址：
  ```
  [000012] I net   : PDP 已就绪，IP=10.x.x.x（Web 面板: http://10.x.x.x:8080）
  ```
  上板后用电脑侧 `ipconfig` 看 RNDIS 网卡网关地址为准。

### 2.4 资源上限是 flash 1024K / ram 512K（不是 1MB/3135KB）

- 权威依据 `prebuild/ld/ML307A/DSLN/app_dsln.ld`：
  ```
  ram   (rwx): ORIGIN = 0x7E380000, LENGTH = 512K
  flash (rwx): ORIGIN = 0x805F8000, LENGTH = 1024K
  ENTRY(cm_opencpu_entry)
  ```
- "1MB Flash" 指的是 **APP 分区**；DSLN 整片 QSPI NOR 是 **8 MiB**（`FLASH_OPT=8M`，
  分区表 `user_app size=1024KiB`）。"3135KB RAM" 在 SDK 里找不到依据（应属 SoC 规格）。
- 影响：你的 750KB 固件目标其实非常宽松——本固件实测 123.5KB。

### 2.5 不需要 Keil

- SDK 全仓库对 `keil / uvproj / MDK` **零命中**；编译器是自带的 `arm-none-eabi-gcc 8.3.1`，
  `-mcpu=cortex-r5`。make / python / arelease 全部自带。
- 影响：不用买/装 Keil，也不用担心 MDK 授权与器件包。

### 2.6 没有可用的"看门狗喂狗"API

- `include/cmiot/` 里没有 `cm_wdt.h`；内核里存在 `watchdogKick/Activate/Configure`（`hal-HAL.lib`），
  但**不在应用链接边界内**。
- 处置：依赖底包自身的 WDT 管理；应用侧通过 `cm_pm_get_power_on_reason()` 识别
  `CM_PM_ERROR_RESET`（WDT 复位）并打日志。**本项须上板验证**：人为写死循环，看是否 60s 复位。

## 三、与原需求文档的差异清单

| # | 原文档写法 | 实际实现 | 理由 | 影响 / 备选 |
|---|---|---|---|---|
| 3.1 | 心跳用 **PING(ICMP)** | 心跳用 **TCP 连通性探测**（`lwip_connect`+`select`） | SDK 无 PING API；`AT+MPING` 属厂商私有指令，虚拟 AT 官方声明仅支持 3GPP，可用性未证实。TCP 探测验证的正是 Webhook 要走的那条数据通路 | 更贴近真实可用性判定；若你坚持 ICMP，可后续用 lwip raw socket 自实现 |
| 3.2 | RNDIS 运行时开关 | 配置期望值 + 重启生效提示 | 链接边界无 RNDIS 符号（见 2.2） | 需底包/NV 支持才能实现；已预留代码位（`sdk_rndis_apply()` 一处即可接上） |
| 3.3 | 短信接收"监听 +CMT" | URC 回调 + `AT+CMGF=0` + `AT+CNMI=2,2,0,0,0`，并保留 `+CMTI`→`AT+CMGR` 兜底 | SDK 无收短信 API，只能走 URC（三重核实：头文件/底包符号/官方 chm 手册） | 若你的网络/底包实际投递 `+CMTI`，兜底路径同样能收到 |
| 3.4 | "读取 PDP 上下文上下行流量" | 平台导出计数 `get_rx_byte_all()/get_tx_byte_all()` + 应用侧基线差值 | 头文件里的 `lwip_nwst_get_used_data()` **不在应用链接边界内**（实测 undefined reference）；这两个导出函数是边界内唯一的字节计数 | 上下行分方向统计**反而可用**（原以为不行）。语义待上板确认（见 `docs/04`） |
| 3.4 | 月度限额用平台侧阈值 | 应用层按采样周期判定 + 主动断网 | `lwip_nwst_set_cutoff_data()` 同样不在应用边界内 | 逻辑等价，只是断网动作由应用发起 |
| 3.6 | "片内 Flash 开辟 **4KB 扇区**存储结构体" | 用 SDK 的 `cm_fs` 文件系统，**主/备/临时三文件原子写** | SDK **不暴露裸扇区擦写接口**（只有 `cm_fs.h`）；且 `cm_fs_sync` 被 `#if 0` 禁用，落盘依赖 `close()` | 擦写寿命由文件系统管理，逻辑上等价于"仅在保存/重置/超限时写"；三文件方案能抗掉电写坏 |
| 3.6 | MMC-SD 持久化（可选） | 未实现 | 属可选扩展；`cm_sd.h` API 在边界内，可后续接入 | 需要底板有 SD 卡座 |
| 3.7 | 看门狗 60s，任务循环内喂狗 | 依赖底包 WDT，应用层识别复位原因 | 无应用层喂狗 API（见 2.6） | 须上板验证 60s 是否真的会复位 |
| 6.4 | HTTPS Webhook（可选扩展） | **已实现**，含证书策略（优先 `ca.pem` 校验，否则关闭校验并告警） | 企业微信/钉钉本身就是 https，不得不做 | 见 3.9 |
| 6.1/6.3/6.5/6.6 | LED / 定位 / 短信指令 / 长短信重组 | 未实现（属可选） | `cm_gpio.h` / `cm_lbs.h` 均在应用边界内，接口已预留 | 长短信当前只标记分片不重组（符合原文档 3.5） |

### 3.9 HTTPS Webhook 的证书策略（已实现）

企业微信与钉钉的机器人地址都是 `https://`，因此本固件必须处理 TLS。实现方式
（`app/src/sdk_port.c` 的 `https_prepare_verify()`，每次 https 请求前调用一次）：

| 优先级 | 条件 | 行为 |
|---|---|---|
| 1 | 文件系统里存在根证书 `ca.pem` | 用 `cm_ssl_setopt(id, CM_SSL_PARAM_CA_CERT, pem)` 装入，并置 `CM_SSL_PARAM_VERIFY = 1`（单向校验）→ 日志：`已装入根证书 ca.pem（N 字节），HTTPS 开启单向校验` |
| 2 | 没有 `ca.pem` | 置 `CM_SSL_PARAM_VERIFY = 0`（不校验证书）→ 保证可用，并**每次上电告警一次**：`未找到根证书…HTTPS 已关闭证书校验。生产环境请把根证书写入 ca.pem 后重启以开启校验` |

依据 `include/cmiot/cm_ssl.h`（原文）：
```
CM_SSL_PARAM_VERIFY  : 值类型 uint8_t，0 无身份验证 / 1 单向验证 / 2 双向验证
CM_SSL_PARAM_CA_CERT : 值类型 char*，CA 证书字符串指针
int32_t cm_ssl_setopt(int32_t ssl_id, cm_ssl_param_type_e type, void *value);
```
`cm_ssl_setopt` 已确认**在应用链接边界内**（`docs/sdk-reference/app-link-symbols.txt`），可正常链接。

**权衡说明**：方案 2 牺牲了证书校验。对"只往固定机器人地址推消息、走内网 RNDIS"的网关，
先保证可用 + 日志显式告警是合理的第一步；要收紧安全，把根证书写入 `ca.pem` 即可，无需改代码。

**上板需确认**：`CM_SSL_PARAM_VERIFY` 是否必须早于 `cm_httpclient_sync_request()` 设置、
以及 `ssl_id` 与 `cm_httpclient_cfg_t.ssl_id` 的对应关系。若握手仍失败，把 `ping_target`
或 Webhook 先指向一个 **http** 中转服务做功能验证，再单独排查 TLS。

## 四、原文档"八、待确认项与风险"的逐条回答

| 原文档问题 | 答案 |
|---|---|
| 1. SDK 是否有 RNDIS 运行时开关 API（`cm_usb.h`）？ | **没有**。且不是"头文件没暴露"——是**应用链接边界内没有符号**，`cm_usb.h` 在 1.4.2 里也不存在（1.4.3 新增的 `cm_usb.h` 只是 USB 虚拟串口，与 RNDIS 无关）。→ 走"默认 + 重启生效"分支 |
| 2. RNDIS 默认 IP 与 Web 端口？ | Web 端口 = **8080**（本工程实现）。默认 IP：`192.168.0.1` **证伪**；候选 `192.168.0.1`（/16），但那是 AT 帮助文本，**须实测确认**。固件会自动打印真实 IP |
| 3. Flash 擦写寿命？ | 已优化：仅在保存配置 / 重置流量 / 超限阈值变化时写；且采用临时文件+回读校验+主备轮换，抗掉电 |
| 4. 长短信？ | 按原文档：不重组，但**识别并标记**分片（`seq/total`），Web 与导出里可见 |
| 5. 无 BOOT/RST 按键怎么进下载模式？ | 首选软入口 **`AT$MYDOWNLOAD=1`**（该 AT 命令在底包中真实存在）；备选触点需查原理图，本工程不臆造编号 |

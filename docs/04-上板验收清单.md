## 第 1 步 · 上电与日志 ⚠（先确认能看到日志，否则后面全是盲调）

| 项 | 操作 |
|---|---|
| 接线 | USB 接底板；日志口 = **UART0**（IOMUX PIN_17/PIN_18），**921600** 8N1 |
| 工具 | 任意串口助手；若用 USB CDC，先在设备管理器找 COM 号 |

**预期输出（开机约 20 秒内）**：
```
========================================
 ML307A-DSLN 4G SMS Gateway  (OpenCPU)
 firmware v1.1  build ...
========================================
[000000] I boot  : 上次复位原因: 正常上电
[000000] I cfg   : Flash 中无有效配置，写入默认配置（首次上电）
[000000] I rndis : 本底包未向应用导出 RNDIS 控制接口：USB 流量共享无法由固件切换。
[000000] I traffic: 流量统计就绪：平台计数 rx=… tx=… 字节，本月累计 0 KB
[000000] I sms   : 短信服务就绪（PDU 模式 + URC 上报）
[000000] I net   : 网络管理启动：APN=cmnet 心跳目标=www.baidu.com:80 周期=300000 ms
[000000] I web   : Web 管理服务已初始化（端口 8080）
[000000] I main  : 初始化完成：短信 / 网络保活 / 流量管理 / Web 面板 已全部启动
```

判定：
- ✅ 能看到以上日志 → 继续
- ❌ 完全没有日志 → 日志通道问题。按 `app/src/sdk_port.c` 顶部注释切到
  `drv_uart.c` 的 `uart_open(CM_UART_DEV_0, 921600, u0_callback)` + `u0_printf()` 方案，
  或先确认波特率/引脚。**此步不通，后续所有验证都无法进行。**

## 第 2 步 · 网络与 APN

| 观察点 | 预期日志 |
|---|---|
| 注册与信号 | `I net: 网络状态：注册=是 CSQ=22 IP=10.x.x.x 在线=否` |
| PDP 就绪 | `I net: PDP 已就绪，IP=10.x.x.x（Web 面板: http://10.x.x.x:8080）` |
| 心跳 | `I net: 心跳 www.baidu.com:80 -> 可达（耗时 312 ms）` |

验证项：
1. **注册状态是否正确**：拔掉 SIM / 换无效卡，应看到 `注册=否` 且累计失败后
   `W net: 网络异常（未注册/未附着），自动切换 APN -> 3gnet`。
2. ⚠ **`AT+CGPADDR=1` 是否返回 IPv4**：若 `IP=(无)` 一直不变，说明该指令在本底包上
   行为不同（虚拟 AT 只保证 3GPP 标准指令）。备选：改用 `AT+CGDCONT?`/`AT+CGPADDR?`，
   或列出所有可用 PDP（打印原始应答便于排查 —— 固件已把 AT 应答存入 `smspdu` 同级的
   日志路径，可在 `sdk_net_local_ip()` 里临时加 `LOG_D` 打印 `resp`）。
3. **心跳可达性判定是否符合直觉**：把 ping_target 改成不存在的域名（`Web→配置`），
   应看到 `心跳 … -> 不可达`，连续 3 次后切 APN。

## 第 3 步 · Web 面板与登录 ⚠

1. **先确定网卡与网关 IP**：电脑上 `ipconfig /all`，找 RNDIS/USB 网卡，记下
   **默认网关**（这是本项要确认的关键数据，预期 `192.168.0.1` 或其它）。
2. 浏览器访问 `http://<网关IP>:8080/`
3. 用默认口令 `admin123` 登录

| 检查项 | 判定 |
|---|---|
| 登录页有**输入框和按钮** | 若只有样式没有表单 → 说明页面被截断（该缺陷已修，若复现请回报 `web_ui_login_page` 的返回长度） |
| 登录成功跳转 `/` | 口令错误应显示"口令错误，请重新输入" |
| 状态页显示 | 网络在线/离线、当前 APN、CSQ、USB 共享状态、IP、IMEI、运行时长、当前时间 |
| 流量卡片 | 本月已用 / 限额（进度条）、上行、下行、会话合计 |
| 点【切换下一个 APN】 | 日志出现 `I net: 正在切换到 APN: 3gnet`，配置落盘 |
| 点【导出短信日志】 | 下载 `sms_log.txt` |
| 点【重置本月流量】 | 本月已用归零 |
| 保存配置后**断电重启** | 配置仍然生效（验证 Flash 持久化） |
| 点【重启模组】 | 先看到提示文本，然后模组重启 |

**记录**：RNDIS 网关实际 IP = `________`（用来更新文档与 README）

## 第 4 步 · 短信接收与 Webhook 推送 ⚠

前提：配置好 Webhook（企业微信/钉钉机器人地址），或先指向一个可接收请求的
**http** 测试服务（因为 HTTPS 的 CA 证书尚未配置，见 `docs/03` 第 3.9 节）。

用另一部手机向模组 SIM 号发送短信，分别测：
1. 纯英文短信
2. 中文短信
3. 含扩展字符：`^ { } \ [ ] ~ | €`
4. 一条长短信（会被拆成多片）

| 检查项 | 预期日志 |
|---|---|
| URC 到达 | `D sms: URC: +CMT: ,25` 随后 `I sms: 收到短信 号码=+86… 时间=… 编码=UCS2 长度=…` |
| 正文正确 | `D sms: 内容: 你好世界`（**中文不乱码**） |
| 推送成功 | `I sms: Webhook 推送成功（HTTP 200）` |
| 黑白名单 | 加黑名单后应 `W sms: 短信被拦截（blacklist）：…` |
| 长短信 | 日志标注`（长短信分片，本版不重组）`，Web 列表显示 `[长短信 n/N]` |

**若收不到短信**（最可能的情况），按此顺序排查：
1. 看是否有 `+CMTI:` 而不是 `+CMT:` → 说明底包实际是 mode=1，兜底路径会走
   `AT+CMGR`（日志会出现 `URC: +CMTI: … -> 使用 AT+CMGR 读取索引 N`），能收到即正常
2. 完全没有 URC → 手工在 CDC 串口敲：`AT+CMGF=0`、`AT+CNMI=2,2,0,0,0`，
   再发短信看串口是否有输出。若手工有、固件没有，则是 URC 注册时机问题
   （`cm_virt_at_urc_reg` 与 `cm_virt_at_init` 的关系待确认，可尝试在 `sdk_at_cmd()`
   每次交互后**都**重新注册 URC —— 固件已这样做，若仍无效请回报）
3. 有 URC 但解码失败 → 把日志级别调到 DEBUG（`app_log_set_level(APP_LOG_DEBUG)`）
   看 `app_log_hexdump` 打出的 PDU 原文，用 `python app/test/gen_pdus.py --dump` 对照

## 第 5 步 · 流量统计语义确认 ⚠（最关键的未文档化项）

`get_rx_byte_all()` / `get_tx_byte_all()` 是**未写入任何 SDK 头文件**的平台导出函数，
链接可用但语义未证实。验证方法：

1. 记录上电后日志里的 `平台计数 rx=… tx=…`
2. 让模组产生**已知的少量流量**，例如：
   - 触发一次 Webhook 推送（约 1~2KB 上行）
   - 用 RNDIS 共享给电脑下载一个已知大小的文件（如 1MB）
3. 等一个采样周期（默认 60 秒），看日志：
   ```
   D traffic: 采样：本月 … KB / 会话 … KB（上 … / 下 …）/ 速率 … B/s
   ```
4. 判定：
   - ✅ 上行计数随推送增大、下行随下载增大 → 语义正确，方向未反
   - ⚠ 两者都没变化 → 该接口在本底包上不生效。**备选方案**：
     （a）用 `AT*DATASTATUS?` 之类底包私有 AT（虚拟 AT 可能不支持）；
     （b）在应用层只统计自己 socket 收发的字节（拿不到 RNDIS 共享流量，需在文档中标注口径）；
     （c）向中移 FAE 索取"用户 APP 可用的流量统计接口"
   - ⚠ 方向相反（下载走上行）→ 把 `traffic.c` 里 `s_session_rx/s_session_tx` 的用法对调即可
5. 另需确认：计数是**自模组启动**还是**自上次清零**。固件已处理"计数回退"（重启归零）情况，
   日志会打 `W traffic: 平台计数器回退（…），重建基线`

## 第 6 步 · 看门狗（需求 3.7 的 60s 超时）

| 步骤 | 操作 |
|---|---|
| 1 | 在 `net_mgr_task` 里临时插入 `for(;;) sdk_task_sleep_ms(1000);`（死循环，不喂狗） |
| 2 | 编译烧录，观察是否约 60 秒后自动重启 |
| 3 | 重启后看日志：应出现 `W boot: 上次复位原因: 看门狗/异常复位 (WDT)` |

判定：
- ✅ 会复位且日志正确 → 看门狗由底包负责，应用无需喂狗
- ❌ 不复位 → 需要应用层显式喂狗，但**当前 SDK 未向应用导出喂狗接口**，
  需向中移 FAE 确认（或评估通过 `cm_pm_work_lock()` 等维持运行）

# 06 · 首次上电重启循环：定位与修复

> 现象发生时间：2026-10-14 18:20（`BOOT_MODE` 短接后首次烧录成功）
> 结论：**应用侧两处不符合 SDK 契约的写法**，已修复并重新编译验证。

---

## 一、现象

用官方 `adownload.exe` 烧录完整包成功（日志 `"status": "SUCCEEDED"`、`all finished. total time: 28.108s`）后，
模组**反复重启**，周期约 15 秒。设备枚举采样：

```
[ 3s] PID=[]                            COM=[]              RNDIS=0   ← 掉线
[ 6s] PID=[3012]                        COM=[]              RNDIS=0   ← 重新枚举
[ 9s] PID=[3012, MI_00, MI_02, MI_04]   COM=[]              RNDIS=0   ← 内核与 USB 功能正常
[12s] PID=[3012, MI_00, MI_02, MI_04]   COM=[COM3]          RNDIS=1   ← RNDIS 起来了
[15s] PID=[3012, MI_00, MI_02, MI_04]   COM=[COM3]          RNDIS=1   ← 稳定约 6 秒
[18s] PID=[3012, MI_00, MI_02, MI_04]   COM=[]              RNDIS=0   ← 崩溃复位
[24s] PID=[]                            COM=[]              RNDIS=0   ← 循环
[27s] ...（重复）
```

**判读**：`PID_3012` + RNDIS + COM3 都能正常出现 ⇒ **内核烧写正确、USB 功能正常**；
起来约 6 秒后复位 ⇒ **问题在应用侧**（内核不会因为应用没跑而复位）。

---

## 二、根因 1（主因）：`cm_virt_at_init(NULL)` 违反 SDK 契约

SDK 官方虚拟 AT 示例 `custom/drv/uart/drv_virt_at.c` 的写法：

```c
unsigned char at_data[256] = {0};

static void oc_resp_cb(void *param)          /* 响应回调 */
{
    if (atoi(param) == OC_RESP_OK)           /* 参数是响应码字符串 */
        get_len = cm_virt_at_get(at_data, sizeof(at_data));   /* 数据在回调里取 */
    ...
    cm_virt_at_deinit();                     /* deinit 也在回调里做 */
}

int my_virt_at_test(unsigned char *cmd, int len)
{
    ...
    if (cm_virt_at_init(oc_resp_cb) != 0)    /* ★ 必须传回调 */
        return -1;
    send_len = cm_virt_at_send((uint8_t *)at_operation, sizeof(at_operation));
    osDelay(2);
    ...
}
```

**修复前的实现**：

```c
if (cm_virt_at_init(NULL) != 0) return -1;    /* ★ 传了 NULL */
...
while (waited < timeout_ms) {                 /* 在自己的线程里轮询 get() */
    n = cm_virt_at_get((unsigned char *)rx, (int)(sizeof(rx) - 1u));
    ...
}
```

**问题**：内核在收到命令响应（或上报）时会回调注册的响应函数。传 `NULL` ⇒ 调用空函数指针
⇒ **硬故障 → 模组复位**。响应在模组注册上网前后立刻到达（`+CEREG` / `+CGEV` 等），
与"起来约 6 秒后崩溃"的时间特征吻合。

### 修复后（`app/src/sdk_port.c`）

- 新增响应缓冲区 `s_virtat_rx[256]`（与官方示例同尺寸）
- 新增 `virt_at_resp_cb(void *param)`：解析响应码 → 在**回调内** `cm_virt_at_get()`
  → 置完成标志 → **在回调内** `cm_virt_at_deinit()`
- `sdk_at_cmd()` 改为：`init(cb)` → `send()` → 等待回调完成（10ms 轮询 + 超时兜底）
  → 取出数据 → 补注册 URC → 解锁
- 删除失效的 `at_ensure_ready()`（含 NULL init）与不再使用的 `contains()`

## 三、根因 2（次因）：入口函数里做了大量阻塞操作

**修复前** `cm_opencpu_entry()` 顺序执行：读 Flash 配置（含首次写入默认配置）、
USB 配置、流量统计读平台计数、短信通道（`AT+CMGF=0` + `AT+CNMI=2,2,0,0,0`，单条超时 2000ms）、
网络初始化、Web 初始化，最后才建任务 —— **累计阻塞可达十几秒**。

而 SDK 官方示例（`custom/drv/uart/drv_uart.c`）的入口只做"打开 UART + 创建线程"就 `return`，
把实际工作交给任务。入口长时间不返回会与 SDK 的启动流程冲突（也可能触发启动超时保护）。

### 修复后（`app/src/main.c`）

```
cm_opencpu_entry()             // 只做两件事，立即 return 0
   ├─ app_log_init()           // 无阻塞，打印开机横幅与复位原因
   └─ sdk_task_create("app_main", ...)

app_main_task()                // 真正的初始化，运行在任务上下文
   ├─ sdk_task_sleep_ms(3000)  // 等 SDK 挂载完文件系统/网络栈
   ├─ app_ctx_init()           // Flash 配置
   ├─ usb_rndis_init()
   ├─ traffic_init()
   ├─ sms_svc_init()           // AT+CMGF / AT+CNMI（阻塞在这里是允许的）
   ├─ net_mgr_init() / web_server_init()
   ├─ sdk_task_create("sms_svc" / "net_mgr" / "web")
   └─ traffic_loop()           // 本任务转为流量采样循环（不返回）
```

任务总数不变（app_main/traffic + sms_svc + net_mgr + web = 4），栈合计约 21KB。

## 四、顺带核对过的其它风险点（均已确认无误，无需改动）

| 检查项 | 结论 |
|---|---|
| `osThreadNew` 用法 | 与 SDK `app.c` 一致（`stack_size` + `osPriorityNormal`，栈由 SDK 分配）✓ |
| `cm_log_printf(uint8_t log_level, ...)` | 头文件注明"log 等级暂不支持，传入任意值即可" ⇒ 传 0 安全 ✓ |
| `cm_fs_*` 用法 | 与官方 `cm_demo_fs.c` 完全一致（`cm_fs_exist` / `cm_fs_open(CM_FS_RB/WB)` / `read` / `write` / `close`）✓ |
| `cm_fs_open` 的 flag | SDK 使用 `CM_FS_RB` / `CM_FS_WB` / `CM_FS_WBPLUS` 宏，不是 POSIX `O_CREAT` ✓ |

## 六、复现与验证方法（下次遇到类似问题可直接复用）

1. **判断是不是应用崩溃**：采样设备枚举，若能稳定看到 `PID_3012` + RNDIS + COM3 后周期性消失，
   说明内核正常、应用崩溃；若完全没有 `3012`，问题在内核/烧录。
2. **查 SDK 官方对应示例**：`custom/drv/uart/drv_virt_at.c`（虚拟 AT）、`cm_demo_fs.c`（文件系统）、
   `custom/drv/uart/drv_uart.c`（入口与线程模型）——这是判断 API 契约是否被违反的最快依据。
3. **注意 SDK 的"入口快速返回"约定**：阻塞初始化一律放进任务。
4. **日志通道**：模组 LOG 走 `DBG_UART` 测试点（UART0，921600），不经过 USB；
   没有 USB-TTL 时只能靠枚举行为 + 代码审查定位。

## 八、★ 结论验证：重启循环确由应用造成（回退实验）

### 8.1 回退操作

用厂商原始整包回退（`prebuild/baseline/ML307A/DSLN/ML307A-DSLN-MBRH1S00_2.0.0.2306201630_release.zip`）：

```
18:54:18  (flasher) erase "user_app" done.      ← 应用被彻底移除
18:54:20  (flasher) erase "nvm" done.
          all finished. total time: 26.516s
          "status" : "SUCCEEDED"
```

> 说明：**没有出厂 `MTS` 固件的镜像备份**（刷写前只备份了参数，未 dump flash），
> 所以无法恢复出厂的 AT 指令固件；厂商整包是可得的最接近的干净状态。

### 8.2 回退后的测量（模组内无应用）

```
60 秒稳定性: UUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUUU
             掉线 0 / 60                     ← 重启循环完全消失

AT           -> OK
AT+CGMR      -> ML307A-DSLN-MBRH1S00          ← 内核正常
AT+CPIN?     -> +CPIN: READY                  ← SIM 正常
AT*MRD_IMEI? -> *MRD_IMEI:000000000000000     ← IMEI 与备份一致
AT+CSQ       -> +CSQ: 31,99                   ← 信号正常
```

### 8.3 由此得到的三条确定结论

| 结论 | 依据 |
|---|---|
| **① 重启循环 100% 由应用代码造成** | 同一内核、同一 `nvm`、同一 SIM 条件下，移除应用后掉线 0/60 |
| **② `erase nvm` 不会丢 IMEI/SN** | `*MRD_IMEI` 与备份逐位一致 ⇒ IMEI/SN 存放在 `factory` 分区（升级模式不擦） |
| **③ 之前的 `+CPIN: SIM REMOVED` 是应用崩溃的连带现象** | 回退后 `+CPIN: READY`；应用崩溃导致模组从未走到 SIM 初始化完成 |

⇒ 之前怀疑的"nvm 丢 IMEI 导致 modem 起不来"**被证伪**，真正原因仍在校验修复后的应用代码里。

### 8.4 尚未排除的应用侧可疑点（按可能性排序）

1. **入口未调用 `uart_open(CM_UART_DEV_0, 921600, u0_callback)`**
   SDK 官方入口的第一件事就是打开 UART0（`app.c` 注释明确："串口由于 LOG 功能，
   已在 `cm_opencpu_entry()` 开头初始化"）。本应用未打开即调用 `cm_log_printf()`，
   若内核日志路径依赖该 UART 初始化，可能在内核态出问题。
2. **`get_rx_byte_all()` / `get_tx_byte_all()`（流量统计）**
   `cm_stub_DSLN.o` 导出的未文档化平台计数器，调用时机/前置条件未知。
3. **应用 BSS 体积**（回退后基线 bss 仅约 880B；本应用 bss 100,976B，约 115 倍）
   需确认 `app_dsln.ld` 中 RAM 区确实完整归应用使用，未与内核运行期数据重叠。

### 8.5 下一步（保持稳定优先）

- 首选：接 **DBG_UART**（管脚 17/18，921600）抓取启动日志，一次定位崩溃行；
- 备选：以"最小应用 → 逐步加回模块"的方式二分（每轮需一次 `BOOT_MODE` 烧录）。

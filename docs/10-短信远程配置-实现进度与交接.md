## 二、剩余工作（2 项，均已具备落地条件）

### 2.1 远程配置持久化（模块 5）—— ✅ 已完成（2026-10-15 收尾）

**没有改 `app_config.c`**（其序列化已在主机测试中稳定），而是独立文件 `rcfg.bin`、独立版本号：

- 结构体即 `sms_remote_cfg_t`（url192 / secret80 / keyword40 / tmpl160 / admin24 / ntp64 / concat_enable）
- 落盘布局：`magic(4) + version(2) + len(2) + payload(564) + checksum(4)` = **576 字节**，
  对外公布为 `SMS_RCFG_BLOB_SIZE`；`sms_rcfg.c` 里两条编译期断言保证它与
  `sizeof(sms_remote_cfg_t)`/`sizeof(sms_rcfg_blob_t)` 同步，改结构体忘了改宏会直接编译失败
- 新增接口：
  ```c
  #define SMS_RCFG_BLOB_SIZE 576u          /* 调用方缓冲必须 ≥ 此值（别再用 512！） */
  #define SMS_RCFG_FILE      "rcfg.bin"
  int sms_rcfg_restore(const void *blob, int32_t blob_len, sms_remote_cfg_t *c); /* 1=恢复 0=默认值 */
  int sms_rcfg_save(const sms_remote_cfg_t *c);   /* 序列化 + sdk_file_write，0 成功 */
  int sms_rcfg_load(sms_remote_cfg_t *c);         /* sdk_file_read + restore，1=恢复 0=默认值 */
  ```
- **坏数据不会变砖**：文件不存在、掉电半截写（长度不足）、magic/版本/校验和损坏，全部静默回退默认值
- 576 字节缓冲放在模块级静态区（短信任务栈预算只有 3072，占栈会挤爆），调用点只有启动载入与
  短信任务收到 `SAVE`，二者不并发，故未加重入锁
- 好处：不动既有配置格式，零回归风险；`sdk_file_write()` 自带"回写 32 字节抽查"

### 2.2 集成 A：`sms_svc` —— ✅ 已完成（2026-10-15）

落地位置：`app/src/sms_svc.c`（+ `app/src/sms_admin.c` 承载可测的决策逻辑）。

1. **分片重组**：`handle_pdu()` 解码后若 `pdu.concat.present && rcfg.concat_enable` →
   `sms_concat_feed(&pdu, &cmsg, sdk_uptime_ms())`：
   - `BUFFERED` → 计数并返回（不入缓存、不转发）；
   - `COMPLETE` → 用 `cmsg.text/number/scts` 作为完整短信，标记"已收齐 total/total"；
   - `ERROR` → 丢弃并计入 `concat_drop`。
   `sms_svc_task()` 每轮（1 秒）调用 `sms_concat_tick()` 释放 30 秒未收齐的槽位。
2. **远程配置**：`sms_svc_init()` 启动时 `sms_rcfg_load(&s_rcfg)`（返回 0 = 首启/损坏，已是默认值）；
   收到 `SAVE` 才 `sms_rcfg_save()` 落盘（不无谓擦写 Flash）。
3. **指令分发**：`sms_admin_handle(&s_rcfg, 号码, 完整正文, &view, &out)`：
   - 非管理员 → `is_admin=0`，走原转发流程，**改不动配置**（主机测试 `[7]` 已证明越权无效）；
   - 管理员 → 逐行 `sms_cmd_parse()` → `sms_rcfg_apply()` → 合并回执；
     `SAVE` 置 `need_save`、`RESET` 置 `need_reboot`；
   - 管理员短信**不转发**（它是配置指令，回执即响应）。
4. **回执发送**：`send_reply()` → `AT+CSCA?` 取短信中心（开机读一次，失败后 60 秒限速重试）→
   `sms_concat_build_tx(sca, dst, text, ...)` 分包 → 逐片 `sdk_sms_send_pdu()`，片间 300ms；
   静态 8×640 字节 PDU 缓冲，不占短信任务栈。
5. **视图**：`build_view()` 组装 网络/信号/对时 状态 + `收/转` 计数，供 `我要配置`、`STATUS` 渲染。
6. **统计**：`sms_stat_t` 新增 `parts / reassembled / concat_drop / admin_cmd / replies / reply_failed`，
   并在短信日志导出里输出。

#### 集成时修掉的一个真缺陷（sdk_port）
`sdk_sms_send_pdu()` 原本把手持的 **SCA 号码串** 传给 `cm_virt_at_sms_send()` 的第一个参数
`atCmgs`。而官方注释写明该参数是「`AT+CMGS=` 之后的参数」，PDU 模式下应为 **PDU 的八位组长**
（会拼出 `AT+CMGS=+8613800738500`，属非法指令）。该函数此前**无任何调用者**，因此在首次使用前
改为传 `strlen(pdu_hex)/2`，并且 SMSC 由 `sms_concat_build_tx()` 写进 PDU 首部。
签名随之简化为 `int sdk_sms_send_pdu(const char *pdu_hex)`。
⚠ `atCmgs` 的确切语义仍属**未上板证实**项（`docs/research/01` 未证实清单第 4 条），烧录后第一条回执即可验证。

### 2.3 集成 B：`webhook` —— ✅ 已完成（2026-10-15）

落地位置：`app/src/webhook.c`（新增纯函数 `webhook_build_forward()` + `webhook_send_request()`）、
`app/src/app_time.c`（新增）、`app/src/sdk_port.c`（时钟同步）、`app/src/sms_svc.c`（转发路径切换）。

1. **组装顺序**（`webhook_build_forward()`，纯函数、无 I/O）：
   模板渲染（`webhook_render_template`）→ 关键词注入（`webhook_apply_keyword`，得到 `【kw】正文`）
   → 包成机器人 JSON（钉钉/企业微信/通用的结构差异复用原有 `build_payload`）→ 加签 URL。
2. **取值优先级**：短信里设的远程配置优先（`rcfg.url/secret/keyword/tmpl`），
   为空时回落到 `app_config` 的 `webhook_url`；开关仍看 `webhook_enable`。
3. **加签与降级**：`secret` 非空 **且** 时钟可信才加签；否则
   `req.sign_downgraded = 1`、URL 不带 `timestamp/sign`，日志打
   `已配置加签密钥但时钟不可信 -> 本条降级为仅关键词`，状态回执里显示 `未对时(加签已降级)`。
   毫秒时间戳 = `app_time_to_ts_ms(sdk_utc_seconds(), sdk_uptime_ms())`。
4. **对时（NTP）**：`sdk_time_sync_start(server)` 把 `cm_ntp_sync()` **投递到 eloop 线程**执行
   ——`cm_ntp.h` 明说 NTP 依赖 asocket + async_dns + eloop，而 docs/08 已证实应用侧 socket 只能
   在 eloop 线程内操作（否则模组复位），因此沿用 `sdk_srv_start()` 的
   `cm_eloop_register_event + cm_eloop_post_event` 同一套做法。
   结果由 `cm_ntp_set_cfg(CM_NTP_CFG_CB, ...)` 回调写入状态（`sdk_time_sync_state()`：
   0 进行中 / 1 成功 / -1 失败）；回调里还会自己解析 ISO-8601 并 `cm_rtc_set_current_time()` 兜底
   （`CM_NTP_EVENT_SETTIME_FAIL` 分支）。
   另加一条**零依赖**的兜底：`sdk_time_sync_from_modem()` 走 `AT+CCLK?`（入网即有网络时间），
   开机优先尝试它，失败才转 NTP。
5. **触发时机**：`main.c` 在 `net_mgr_init()` 之后主动调一次 `sms_svc_time_sync_try()`；
   短信服务任务每秒也会调用（内部限速：失败最多每分钟重试一次，不会刷 AT）。
6. **统计**：转发成功/失败沿用 `forwarded/failed`，日志区分"已加签"与"降级"。

#### 主机可验证的部分（`[9]`/`[10]` 段，共 66 项断言）
远程配置优先于 `app_config`、模板/关键词/`{pdu}`/`{idx}` 占位符、加签 URL 含
`timestamp=<ms>&sign=<urlencoded base64>`、**有密钥但时钟不可信必定降级且 URL 无 timestamp**、
企业微信与钉钉两种 JSON 结构、超长正文返回失败、时间解析锚点（含 2100 非闰年）与可信区间。

⚠ 仍然只能上板确认的：`cm_ntp_sync()` 在本底包上能否真的连通（NTP 走 asocket/DNS，需 PDP 已激活）、
以及钉钉是否接受本地算出的 `sign`。

## 三、端到端验收步骤（烧录后执行）

1. 用 **13800000000** 发短信「**我要配置**」→ 应收到一条（自动分包）的模板+状态短信
2. 回复（可一条多行）：
   ```
   U https://oapi.dingtalk.com/robot/send?access_token=xxxx
   T SECxxxx
   K 报警
   M {from}|{time}|{text}
   SAVE
   ```
   → 应收到 `OK U` / `OK T` / `OK K` / `OK M` / `OK SAVED`（可一条短信多行，合并回执一条）
3. 用**其他号码**给模组发一条短信 → 钉钉群收到消息，正文含「报警」关键词，加签校验通过
   （管理员自己发的配置短信**不会被转发**，只会回执）
   - 若状态回执显示 `未对时(加签已降级)`，则本条只带关键词、不带 `timestamp/sign`：钉钉若开启了
     「加签」安全设置会拒收，此时应先在 Web 面板/短信确认时间，或检查 NTP 连通性
4. 发 `STATUS` → 状态短信显示网络/NTP/配置/收发计数
5. 发 `RESET` → 收到 `OK RESET` 回执后约 3 秒模组重启（回执先发完再重启）
6. 长短信：用超长模板（>67 字）发 `M ...` → 回执自动分包；再给模组发一条 >70 字的中文短信 → Webhook 侧收到的是**重组后的完整正文**
7. 断电重启后发 `STATUS` → 若中间发过 `SAVE`，`U/T/K/M` 应保持（读的是 `rcfg.bin`）
8. 时间：上电后 `STATUS` 里 `NTP:` 应逐步从 `未对时(加签已降级)` 变为 `已对时 YYYY-MM-DD HH:MM:SS`
   （先走 `AT+CCLK?` 模组时钟，未成再走 NTP；失败每分钟重试）

## 四、注意事项（踩过的坑，勿重犯）

| 坑 | 说明 |
|---|---|
| `cm_virt_at` 契约 | 响应回调里**不能**调 `cm_virt_at_deinit()`（内核上下文）；`init` 必须传回调；URC 只注册一次 |
| 应用 socket | 必须在 **eloop 线程**内创建与收发；`192.168.0.1:8080` 因栈分离**不可达**（已二进制证实） |
| 任务栈预算（**重要更正**） | `main.c` 里 4 个任务都申请 6144 字节，但 `sdk_port.c::sdk_task_create()` 会把**实际栈钳制到 3072 字节**（栈由内核堆分配，任务多了 `osThreadNew` 会失败 → web/探针任务建不出来）。所以"6144 够用"是错觉：**任何大对象都不能放栈上**。已加自动防线：`pwsh -File app/test/check_stack_budget.ps1`（`-fstack-usage` 量单函数 + 按调用链求和，预算 单函数 ≤1280 / 链 ≤2048） |
| 栈溢出的真实事故苗头 | 集成"管理员指令 + 回执分包"后实测：`handle_pdu` 一帧 2688 字节、`sms_admin_handle` 3024 字节、`sms_concat_build_tx` 2608 字节、`sms_svc_export` 5936 字节 —— 链式调用 5~6KB，**远超 3072**。主机单元测试完全测不出来（PC 栈 8MB），上板才会崩。已全部改为静态缓冲，修复后各链 224~1472 字节 |
| 日志 | 现场无 USB-TTL，DBG_UART 日志不可见 → 依赖主机单元测试 + 短信/AT 侧外部验证 |
| 测试脚本 | 多个 `rd()` 写进同一 `printf` 参数会因**求值顺序未定义**错位，务必先取变量 |
| 测试缓冲尺寸 | 验证夹具缓冲必须 ≥ `SMS_RCFG_BLOB_SIZE`(576)。曾用 `uint8_t buf[512]` → `sms_rcfg_serialize()` 正确返回 **-1**，负值又被当 `(size_t)` 长度送进 `memcpy` → **0xC0000005 段错误且无任何输出**。两条规矩：①缓冲按尺寸宏给足；②负返回值先判再转无符号 |
| printf 缓冲 | 崩溃时块缓冲的 stdout 会全部丢失（现象是"程序无输出直接退出"）。`host_tests.c` 已 `setvbuf(_IONBF)`，临时夹具也应照做 |
| `cm_virt_at_sms_send` 的第一参 | 官方注释是「`AT+CMGS=` 之后的参数」，PDU 模式下是 **PDU 八位组长**，不是短信中心号码（写号码会拼出非法的 `AT+CMGS=+86...`）。SMSC 走 PDU 首部，已由 `sms_concat_build_tx()` 携带。**已上板证实**：传长度字符串、通道 init 后调用，`ret=0` 且手机收到 |
| ★ **虚拟 AT 的"响应通路"只投递第一个数据突发** | `AT+CMGR` 读一条长短信：模组侧应答 363 字节（外口可验证完整），**应用只拿到 96 字节**（PDU 82/338 字符）；`AT+CMGL=4`（约 800 字节应答）只拿到 **24 字节**，且响应回调只触发 1 次、之后 `cm_virt_at_get()` 永远返回 0。⇒ **长应答读不回来，长短信必须走 URC**：`AT+CNMI=2,2,0,0,0`（`<mt>=2` 直投）经 URC 通路可拿到完整 330+ 字符 PDU（2026-10-15 实测通过）。收发探测手段：`atread`/`rxpdu` 两条诊断上报 |
| ★ 解码器禁止静默截断 | UCS2 的 `TP-UDL` 是**含 UDH 的总字节数**（`UDL=140 = UDH 6 + 正文 134`）。旧代码把正文长度夹到实际字节数 ⇒ 6 字节碎片被当成合法短信 `U h` 执行，**把 Webhook URL 改成了 "h1"**。现在 `UDL > 到手字节` 一律 `SMS_PDU_ERR_TRUNC`，接收路径重读、绝不当指令执行 |
| 测边界要覆盖"截断" | 上述 bug 主机测试全绿却上板出事——因为向量都是**完整** PDU，没有"声明长度 > 实际长度"的用例。已补 3 条回归用例（UCS2/7bit 截断 + 补全后应成功） |
| URC 行缓冲要够大 | 长短信 `+CMT` 的 PDU 行可达 350+ 字符，`SMS_LINE_MAX` 从 352 提到 **512**，否则会在入队时被截断 |
| ★ **发送回调必须"空手"** | `cm_virt_at_sms_send()` 由内核完成 `AT+CMGS= → 等 ">" → 发数据 → 收 OK`，**应答数据必须留给内核读**。若 init 时注册的回调调用 `cm_virt_at_get()`，就会抢走内核要用的数据 → 现象是"**每次开机只有第一次发送成功，之后恒 ret=-1**"（连 28 字节短条也失败）。改为注册**只计数、不取数据**的空回调后，同一开机周期连发两条都 `ret=0`（2026-10-15 实测）。**这是本次最隐蔽的坑** |
| 回执别用 UDH 拼接短信 | 手机要收齐 UDH 分片才显示，缺一片就整体扣住并丢弃 → 用户"什么都收不到"。改用 `sms_concat_build_tx_plain()`（无 UDH，**每条本身就是完整短信**），并把菜单/状态压到 **≤70 个 UCS2 字符**（一条装完） |
| 别自实现 CMGS 分段 | 虚拟 AT 是"一次 init 只能发一段"（内核串 `cm_virt_at_send m_vrit_at_init_flag == 0` 可证）；且流控要求上一段收到**终结响应**才能发下一段，而 CMGS 的 `>` 不是终结响应 → 自实现必然卡死（实测 `r=12/-1/-1`）。**只能用 `cm_virt_at_sms_send()`** |
| CMGS 命令结尾 | `AT+CMGS=<len>` 必须**只以 CR 结尾**；用 CRLF 时多出的 LF 会被当报文第一个字节 → `+CMS ERROR: 304`（外口实测） |
| 收短信要有兜底 | `AT+CMTI` 的 URC 实测会漏（漏过一次，短信留在 ME 存储里）。`AT+CNMI=2,1,0,0,0`（存储+上报）+ sms 任务每 10 秒 `AT+CMGL=0` 轮询，两条路互补（CMGR/CMGL 会把未读置为已读，不会重复处理） |
| 重组缓存占 RAM | `sms_concat.c` 的 `s_slot[4]` 每槽 `part[8][1024]`，实测 **约 33KB bss**（全固件最大单块）。集成后整机 bss 从 ~103KB 升到 ~163KB（可用 RAM 512KB，仍宽裕）。若要压缩：分片缓冲按实际需要降到 ~200 字节或改成"单缓冲 + 偏移表" |
| 长短信"半截"短信 | 分片进缓存期间 `received` **不计数**（另计 `parts`），只有重组完成才作为一条短信入库/转发；30 秒未收齐由 `sms_concat_tick()` 释放并计入 `concat_drop` |
| AT 调用位置 | `build_view()` 会在短信任务里查 `AT+CEREG?`/`AT+CSQ`（各最长 3 秒），与 net_mgr 的 AT 事务由 `sdk_at_cmd()` 内部互斥串行化。只在管理员短信路径触发，频率极低 |
| NTP 必须在 eloop 线程 | `cm_ntp.h` 原文："NTP模块底层依赖asocket、async_dns和eloop模块"。**直接在应用任务里调 `cm_ntp_sync()` 会踩 docs/08 的复位根因**；本工程把它经 `cm_eloop_register_event + post_event` 投递到 eloop 线程（与 `sdk_srv_start()` 同一套做法） |
| 加签与时钟 | 钉钉按**服务器时间**校验 `timestamp`（±1 小时）。时钟不可信时**必须降级为不加签**，否则请求会被钉钉拒收；本工程用 `app_time_is_valid()`（下限 2025-10-09，上限 2100）判定，并在状态回执里如实标注降级 |
| `cm_ntp_set_cfg` 参数类型 | `CM_NTP_CFG_SERVER` 要传 128 字节字符串指针，`CM_NTP_CFG_TIMEOUT` 是整数型参数——**类型在头文件里没写全**，本工程只设 SERVER 与回调，超时用 SDK 默认 3000ms，避免猜类型 |
| 大结构体不要放栈 | `webhook_req_t`（URL 320 + 体 2048 ≈ 2.4KB）、渲染缓冲 2×2KB、`handle_pdu()` 里的 `pdu`/`cmsg`/`cfg_snapshot`/`out`、`sms_admin_handle()` 里的 `sms_cmd_set_t`(1572)/回执缓冲(1200)、`sms_concat_build_tx()` 的 `ucs2`(2400)、`sms_svc_export()` 的 `rows[16]`(5152) —— 全部放静态区。这些函数都只被单一任务串行调用，不存在重入 |
| 构建流水线别截断 | `pwsh -File tools/build_firmware.ps1 \| Select-Object -First N` 会在第 N 条匹配后**终止上游**，把编译进程和日志一起掐掉（本次踩到，日志只剩 276 行）；要过滤就先完整重定向到文件，再读文件 |
| HTTP 的 DNS 优先级 | `cm_httpclient_cfg_t.dns_priority` 填 `0`（用全局）时，**本底包开机默认 IPv6 优先**（`cm_async_dns.h:106`）。查"公网 IPv4 出口"这类回显服务必须显式填 `1`，否则请求可能走 v6 出口、量回来的是 IPv6 地址。详见 `docs/11` §一.5 |

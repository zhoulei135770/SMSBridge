## 五之二、★★ 短信发送根因定位与修复（本轮最重要的成果）

进来时的现象：管理员号发「我要配置」**收不到任何回执**（旧版固件甚至连收到短信都不稳）。

### 诊断手段：应用内诊断上报（这条通道是本次定位的关键）

无 UART 日志可用，于是用工程里既有的 `sdk_diag_post()`：应用把内部状态 HTTP POST 到
`http://192.168.0.100:9090/diag`（PC 的 RNDIS 地址），PC 侧跑 `tools/diag_listen2.ps1` 收。
实测可用（收到 `srv8080 bind=0 listen=0` 等启动上报），从此每一环都有据可查。

### 现象链（全部有 diag 证据）

| 阶段 | diag 证据 | 结论 |
|---|---|---|
| 接收 | `rx num=+8613800000000 len=12 text=我要配置` | 接收/解码正常 |
| 但 URC 会丢 | `poll unread: +CMGL: 1,0,,28` | **+CMTI 漏过一次**，靠 10 秒轮询兜回 |
| 判定 | `admin=1 changed=0 save=0 reply_len=346` | 管理员判定与回执生成正常 |
| 分包 | `tx_reply dst=… parts=4 sca=+8613800738500` | 分包与短信中心正常 |
| 发送 | `sms_tx len=163 rc=-2 resp=`（空） | 自实现"分三段发"全超时：**虚拟 AT 一次 init 只能发一段** |
| 发送 | `sms_tx sdk … init=0 ret=0` 仅第 1 条 | SDK 封装可用，但**每次开机只有第一次成功** |
| 发送 | `tx init=0 ret=0 len=147 cb=0` ×2（同周期两条都成功） | **修复后：同一开机周期可多次发送** |

### 三个真实缺陷（逐个修掉）

1. **UDH 拼接短信 + 只发出第 1 片 = 用户什么都看不到**
   手机要收齐 UDH 分片才显示，缺片就整体扣住然后丢弃。
   → 回执改为**每片独立成一条短信**（`sms_concat_build_tx_plain()`，无 UDH）。
2. **回执太长（346 字节 → 4 条）**：多发一条就多一次失败机会。
   → 菜单压到 **62 个 UCS2 字符**、状态压到 **47 字符**，各自**一条短信装完**
   （`sms_cmd_build_menu/status()`；状态里模板只显示"已设置/未设置"，时间戳去掉）。
3. **★ 根因：`cm_virt_at_init()` 注册的回调抢走了内核自己要读的模组应答**
   `cm_virt_at_sms_send()` 由内核完成 `AT+CMGS= → 等 ">" → 发数据 → 收 OK` 全流程，
   它需要读走应答；我们的回调却调用 `cm_virt_at_get()` 把数据取走了 → 内核判定失败。
   表现为"每次开机第一次发送侥幸成功、之后恒 ret=-1"（连 28 字节的短条也失败）。
   → 发送路径改为注册**空回调**（只计数、不取数据）：**同一开机周期连发两条都 `ret=0`** ✓

### 其它被实测否定的方案（避免以后重复踩）

| 方案 | 结果 |
|---|---|
| 自实现"发命令 → 等 `>` → 发 PDU → Ctrl-Z"（分三段 `cm_virt_at_send`） | ✗ `r=12/-1/-1`：第 2 段起返回 -1（SDK 流控：未收到终结响应前不许再发） |
| 同上，但每段各自 init/deinit | ✗ 同样 `r=12/-1/-1` |
| 把 `AT+CMGS=N\r` + PDU + Ctrl-Z **拼成一条**交给 `sdk_at_cmd` | ✗ 模组只回 `>`，报文丢失（输入态在提示符之后才收正文） |
| 命令用 CRLF 结尾 | ✗ 多出的 LF 被当报文首字节 → `+CMS ERROR: 304` |
| 批量发送时"整批只 init 一次" | ✗ 封装全部 `ret=-1`（它自己也要 init/deinit，被占着就报 busy） |

### 外口对照实验（用来区分"应用问题"还是"网络问题"）

用 PC 直接驱动模组 AT 口直发短信（绕过应用）：`AT+CMGS=<长度>\r` → 等 `>` → PDU → Ctrl-Z
→ `+CMGS: 25/27` + `OK`，**用户手机收到**。由此确认"模组→手机"投递无问题，
问题确实在应用侧，避免了往 SMS 中心/SIM 方向误查。

## 五之三、★★★ 长短信收不到：SDK 虚拟 AT "响应通路只投递第一个数据突发"

**现象**：管理员发**含长 Webhook URL 的配置短信**（手机按长短信 2 片发出）后，
应用只拿到 4 个字符 `U h1` —— 竟然把半截 URL 当成指令执行了。

### 定位过程（全部有 diag 证据）

| 证据 | 说明 |
|---|---|
| `rxpdu … PDU=0891…8C 05 00 03 0B 02 01 0055 0020 0068` | 应用收到的第 1 片：**UDL=140（应带 134 字节正文），实际只有 6 字节**：U、空格、h |
| 外口 `AT+CMGR=2` 读同一份存储 | **完整 338 字符 PDU**（应答 363 字节）⇒ **截断在应用侧，不在模组/存储** |
| `atread AT+CMGL=4 cb=1 drain=0 len=24` | 控诉式证据：约 800 字节的应答，回调只触发 1 次、补读 0 字节、**只拿到 24 字节** |

⇒ SDK 虚拟 AT 的**响应通路每次只投递第一个数据突发**，`AT+CMGR`/`AT+CMGL` 这类长应答
注定残缺（长短信永远读不回来）。

### 解法：改走 `+CMT` 直投（URC 通路）

`AT+CNMI=2,2,0,0,0`（`<mt>=2`）让模组把整条 PDU 通过 **URC 通路**
（`cm_virt_at_urc_reg` → 逐行回调）推上来，不受响应通路限制：

```
rxpdu dcs=8 enc=2 udhi=1 udhl=5 cat=1 seq=1/2 ref=13 PDU=(完整 330+ 字符)
rxpdu …                                 seq=2/2 ref=13 PDU=(完整)
rx num=+8613800000000 len=136 text=U https://oapi.dingtalk.com/robot/send?a…
admin=1 changed=1 save=1        ← 完整解析 + 写入 flash
tx init=0 ret=0 len=83          ← 回执发送成功
```

代价：`mt=2` 按标准不落存储，URC 丢了就没了（应用仍保留 `AT+CMGL=0` 轮询兜底，
并会把截断 PDU 明确上报 `urc pdu trunc`，绝不静默执行半截内容）。

### 顺带修掉的两个真缺陷

1. **解码器不能静默截断**：UCS2 的 `TP-UDL` 是**含 UDH 的总字节数**（`UDL=140 = UDH 6 + 正文 134`）。
   旧代码把正文长度"夹到实际字节数"，于是 6 字节碎片被当成了合法短信。
   现在 `UDL > 实际到手` 一律返回 `SMS_PDU_ERR_TRUNC`，接收路径**重读**而不是执行，
   URC 内联 PDU 截断则丢弃等轮询重读。
2. **UCS2 UDL 语义**修正后由主机 `pdu_vectors.h` 的 48 组向量拦下（第一版判据写错，
   是测试把它挡回来的），并补了 3 条"截断必须报错"的回归用例。
